## 二、 分章节核心写作规范与实战纠偏铁律

### 2.1 主标题与小标题命名纠偏
1. **主标题优先用「痛点冲突问句」而非「平淡结果陈述」**：
   - ❌ 纠偏前：`刷新页面，AI 回答还在继续：Redis Stream 断线续传与公开发布｜Agent 平台(二)`
   - ✅ 确定版：`刷新页面，AI 回答消失了？Redis Stream 断线续传与公开发布｜Agent 平台(二)`
2. **第二章标题聚焦「业务动作」，严禁暴露“伪代码”字眼**：
   - ❌ 纠偏前：`## 二、10分钟实战：4 段核心业务伪代码拆解`（标题发虚，降低点击与复现欲）
   - ✅ 确定版：`## 二、10分钟实战：4 步实现断连续传`（在章节导语里再自然说明用精炼业务流伪代码呈现主干）

### 2.2 第一章（架构设计）：重思路、重对比、比喻体系统一
1. **必答「为什么选它而不是替代方案」**：
   - 讲核心技术选型前，先用精炼列表回答读者第一直觉疑问（如选 `Redis Stream` 前，先对比为什么不用 `Pub/Sub` 和 `List`）。
   - **底层机制表述必须严谨**：例如 `Pub/Sub` 是基于通道广播、不持久化消息（“发出去就没了”），**严禁写出“Redis 里根本不会建 Key”这类外行话**。
   - 若同一组件有两种用法（如任务流 `XREADGROUP` 抢单 vs 结果流普通 `XREAD` 重放），必须显式点破故意差异化设计的用意。
2. **善用生活化具象比喻，且比喻体系严禁混杂**：
   - 鼓励用生活场景降维复杂异步架构（如后台 `Worker` 线程 vs `SSE` 线程 ➔ 餐厅里的「**厨师**」和「**传菜员**」，去掉“各司其职”等冗余书面修饰；提前插空记录拿 ID ➔ 餐厅「**占座号**」；流式游标 ID ➔ 群聊「**续传书签**」）。
   - **比喻统一铁律**：总起写“两个核心标识”，子标题就严格用 `#### （1）标识一：...` / `#### （2）标识二：...`，**严禁中途混入「钥匙一 / 钥匙二」** 造成多重比喻打架。
3. **消除阅读黑盒，讲清关键参数来源与形态**：
   - 对读者容易困惑的运行时变量，必须举例写明：它是何时生成的？长什么样？（例如明确写出 `msgId=108` 是调大模型前事务插入助手空记录生成的自增主键 `107、108...`；`lastEventId` 不是 `1、2、3`，而是 Redis 自动生成的 `1762415627891-0` 毫秒时间戳序号；明确谁和大模型通信）。
4. **图表与正文一致性**：
   - 时序图横向参与者控制在 3~4 列，连线文字精短（手机竖屏友好）；若图中对长 ID 做了简写（如 `1762415-0`），必须在引出句注明 `（图中 ID 做了简写）`，防止与正文完整格式前后矛盾。

### 2.3 第二章（10分钟实战）：核心业务流伪代码化（篇幅减负铁律）
1. **先给 `tree` 目录，再给 3~4 段精炼业务伪代码**：
   - 先用 10 行以内的 `tree` 展示 `business/{module}`（业务编排层）与 `business/harness/{module}`（运行时支撑层）的代码落位。
   - **拒绝百行源码刷屏**：剥离繁琐的框架序列化、空值防御、监控埋点样板，每步只贴 **10~15 行核心业务流伪代码**，直击主干逻辑。
   - 导语直接写：`下面剥离繁琐的框架序列化与监控统计样板，用 4 段精炼的核心业务流伪代码把整套机制搭起来（完整源码与工程健壮性处理见文末专栏仓库）。`（删掉“为了让大家在手机上一眼看懂”等教学腔）。
2. **伪代码严守源码事实底线 + 补充 1 处真实源码微细节**：
   - 简化方法名可以，但**分支语义绝不能违背真实源码**（如源码里人工终止走独立分支不发 `error`，伪代码绝不能把人工终止混进发 `error` 的异常分支）。
   - 在伪代码下方用 1 个自然段点出源码里极具实战价值的微细节（如 `LlmChatTool#computeReasoningDelta` 针对累积思考全文做前缀比对切增量），兼顾清爽观感与源码深度。

### 2.4 第三章（效果实测）：源码 + UI + 截图 100% 事实核查门禁
动笔写第三章前，Agent **必须**先读取后端 Controller、前端 `.vue` 页面、`zh.json` 国际化文件及用户提供的真实实测截图，逐项核对以下 5 点，**严禁凭印象脑补**：
1. **真实接口路径与 HTTP 方法**：核对完整前缀（如 `/chat/session/msgList` 而非 `/session/msgList`；核对 `GET` / `POST`）。
2. **真实页面交互与按钮文字**：核对开关名、列名、按钮文案（如打开「发布状态」开关 + 点击「访问URL」列里的「**前往Agent**」链接；按钮是「**终止**」而非“红色的停止按钮”）。
3. **真实系统提示文案**：核对落库与界面提示原话（如 `本条回复已被人工终止`，严禁瞎编 `> 已终止生成`）。
4. **前后端兜底职责**：核清默认值是谁给的（如前端刷新不传 `lastEventId`，是**后端**兜底成 `"0"`，严禁写成前端默认传 `"0"`）。
5. **截图数据像素级咬合**：用 `read_file` 查看用户放入目录的每一张截图，如实写出图中的提问原话、`sessionId`、`msgId`、耗时指标（`TTFT` / 总耗时）、Network 面板请求流大小等真实信息。**无截图前绝不提前写死虚假画面细节**。

### 2.5 第四章（踩坑复盘）：诚实视角与底层因果讲透
1. **诚实区分「亲身踩坑」与「源码排雷」**：
   - 若是作者实测抓出的 Bug 或提过 PR 的问题 ➔ 标题用 `## 四、我踩过的三个坑`，第一人称复盘。
   - 若是源码注释或架构里已提前防住的工程细节 ➔ **严禁伪造“最初我写代码时报错……”的虚假经历**！标题诚实定为 `## 四、照着写最容易踩的三个坑`，写明是源码里专门防住的细节。
   - 没有把握或未经验证的推断坑点，直接舍弃，绝不硬凑。
2. **三坑格式统一 + 因果链条闭环**：
   - 统一采用 **「1 段故障底层因果说明 + 1 个简短 `>` 灰色解法结论块」**，三个坑格式严格对齐。
   - 底层原因必须把“为什么会报错”的中间机制讲白（如 `interrupt()` 后线程带着中断标志进 `finally`，导致连接池阻塞等待抛 `InterruptedException`，所以落库前必须先调 `Thread.interrupted()` 清标志）。
3. **不写具体源码行号**：只写类名与方法/字段名（如 `ChatStreamTool` 的 `runContexts`），防止分支演进后行号漂移失真。

### 2.6 第五章（总结与扩展）：双点精炼留白（拒绝沉重 Bug 清单！）
1. **三件套金句收束**：用 `>` 引用块一句话串起本篇 3 个核心支点，句尾用干脆的 `……就算立住了。`（去掉“稳稳立住了”，且每篇变换起手句式，避免篇篇复读第 1 篇的“底层逻辑一点都不玄乎”）。
2. **进阶思考严格「断舍离为 2 个，总字数 80~120 字封顶」**：
   - **设计初衷**：第五章读者认知已饱和，此处旨在**激发想象空间、留白展示架构视野**，绝不是贴一份 450 字的内部 Code Review 缺陷排查单！
   - **筛选标准**：砍掉偏 UI/产品体验的小优化（如异步起标题），只保留 **2 个与本篇核心技术强闭环的硬核生产命题**（如分布式高可用 + 公网安全风控）。
   - **标准模板**：

3. **纯净版文末签名档（固定模板，严禁乱加图标）**：

## 四、 中文 Markdown 排版防崩铁律（SyncCaster / 微信编辑器零错位门禁 🚨）

### 4.1 严禁 `汉字` 与 `标点` 夹击 `**`（CommonMark 双向边界陷阱）
在 SyncCaster、`marked`、`markdown-it` 等标准解析器中，加粗界定符 `**` 只要内侧紧挨着标点符号（如 `「`、`」`、`“`、`”`、`《`、`》`、`（`、`）`），其**外侧就必须是空格或标点**；若外侧紧挨普通汉字，解析器会拒绝识别该 `**`，直接输出字面量 `**`，并引发整段后续所有 `**` **奇偶反转、雪崩错乱**！

- ❌ **两类必崩写法（严禁出现）**：
  1. **左边界陷阱（`汉字 + ** + 左标点`，无法开启加粗）**：
     `把**「大模型生成」**`、`拆成**「两拨独立线程」**`、`点击右下角的**「终止」**按钮`
  2. **右边界陷阱（`右标点 + ** + 汉字`，无法闭合加粗）**：
     `，**严禁混入“钥匙”**造成打架`、`把**（默认 600 秒）**删掉`
- ✅ **强制标准写法（两条铁律任选其一，优先法则一）**：
  1. **【法则一 · 首推】标点在外，加粗在内（`**` 内侧只贴汉字/字母）**：
     `把「**大模型生成**」和「**前端网页连接**」`、`拆成「**两拨独立线程**」`、`点击右下角的「**终止**」按钮`
  2. **【法则二 · 书名号或句内含引号需整体加粗时】`**` 外侧强制留半角空格**：
     `作为 **《Spring AI Agent 平台系列》** 的第 2 篇`、`打通 **Agent 免登公开发布** 与 **深度思考流分离** 的`

### 4.2 终稿交付前强制自动化扫描（Pre-Delivery AST Gate）
每次生成或修改系列文章后，Agent **必须**在交付前运行本技能自带的校验脚本，确认无任何解析残留后方可交付：

```bash
node .agents/skills/agent-platform-series/scripts/check_article.js "docs/wechat/{目标文章}.md"
```
